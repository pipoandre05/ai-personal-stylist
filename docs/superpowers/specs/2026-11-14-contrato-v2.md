## 1. Eventos SSE nuevos (`POST /api/chat`)

Todos viajan como `event: <type>` + `data: <json con "type">`. `CHAT_EVENT_TYPES` se deriva de `ChatEvent`, y el parser (`lib/chat/sse.ts`) los reconoce.
El evento `tool` (`start`/`end`, efímero) **se mantiene** por compatibilidad hasta que la interfaz migre al rastro nuevo.

| Evento | Cuándo | Reemplaza por `id` |
|---|---|---|
| `tool_step` | al empezar (`running`) y al terminar (`done` o `error`) cada paso de trabajo, y otra vez para el paso del clóset cuando se eligen prendas | sí: mismo `id` = reemplaza |
| `event_summary` | el asesor entendió o actualizó el evento | el último gana |
| `outfit` | un look (ahora con `evidence`, `refinements`, `variant`, `pair_id`) | — |
| `search_offer` | el asesor ofrece buscar opciones para la pieza que falta | — |
| `shopping_options` | resultado de una búsqueda (hasta 3 opciones) | por `id` |

### 1.1 `tool_step` (C-1)

```ts
type ToolStep = {
  id: string;                       // único dentro del mensaje: "step-1", "step-2"…
  tool: AgentToolName;              // get_closet | get_weather | propose_outfit | set_event_summary | search_products | add_garment | analyze_palette | remember | update_profile
  status: "running" | "done" | "error";
  label_running: string;            // "Revisando tu clóset"  (sin "…")
  label_done: string;               // "Revisé tu clóset"; puede traer dato: "Miré el clima en Casablanca"
  detail?: string;                  // "32 prendas · 9 sirven para el día · elegí 4"  (solo con done)
  items?: { garment_id: string; chosen: boolean }[]; // solo get_closet: prendas consideradas; chosen = el asesor las usó
};
```

Reglas para pintarlo:

- Ordena por la primera aparición de cada `id`. Un evento con un `id` ya visto **reemplaza** al anterior (no se agrega otro).
- `running` → rótulo `label_running` en gerundio con tres puntos. `done` → `label_done` + `detail`. `error` → solo el rótulo, sin detalle (el asesor sigue sin esa herramienta).
- **El paso del clóset cambia después de terminar**: cuando el asesor propone un look llega otro `tool_step` con el mismo `id` del clóset, con `chosen: true` en las prendas usadas y `· elegí N` en el detalle (con dos looks, N es la unión). Es el que pinta las miniaturas marcadas.
- `search_products` sin búsqueda disponible llega con `status: "error"` y `detail: "La búsqueda no está disponible por ahora"`.
- `suggest_replies` y `offer_search` no dejan rastro (herramientas silenciosas).

Ejemplo (turno real contra el asesor simulado):

```json
{"type":"tool_step","id":"step-3","tool":"get_closet","status":"done","label_running":"Revisando tu clóset","label_done":"Revisé tu clóset","detail":"10 prendas · 8 sirven para el día · elegí 3","items":[{"garment_id":"9c1f…","chosen":true},{"garment_id":"2b7e…","chosen":false}]}
```

"Sirven para el día" = por temporada según el clima y, si el evento pide formalidad, a un nivel de distancia (`servesForDay` en `lib/domain/steps.ts`).

### 1.2 `event_summary` (C-8)

```ts
type EventSummary = {
  kind: string | null;             // "Matrimonio"
  date: string | null;             // "2026-11-21"
  place: string | null;            // "Casablanca" (es el lugar del clima)
  place_note: string | null;       // "En una viña"
  setting: { time_of_day: "day" | "night" | null; venue: "indoor" | "outdoor" | null };
  dress_code: string | null;       // "formal de día" | "no especificado" (la invitación no dice nada)
  weather: { min: number; max: number; note: string } | null; // por lugar Y fecha; null si no hay pronóstico (más de 7 días, o falla)
  missing: ("time_of_day" | "dress_code" | "kind" | "date" | "place" | "venue")[]; // qué falta, en orden de qué preguntar primero; hoy solo salen los cuatro primeros
};
```

```json
{"type":"event_summary","kind":"Matrimonio","date":"2026-11-21","place":"Casablanca","place_note":"En una viña","setting":{"time_of_day":"day","venue":"outdoor"},"dress_code":null,"weather":{"min":13,"max":20,"note":"Nublado"},"missing":["dress_code"]}
```

- **Las cuatro celdas 2×2** ("Lo que entendí") salen de `eventCells(summary)` en `lib/domain/event-summary.ts`: `[{key:"date", title:"Sábado 21 nov", detail:"Matrimonio"}, {key:"place", …}, {key:"weather", title:"11° a 27°", detail:"Despejado · con viento"}, {key:"setting", title:"De día", detail:"Al aire libre"}]`. `title: null` = dato por completar. `field` dice qué campo corrige esa celda. Importa solo lo puro (sin servidor).
- **Corregir un dato**: Server Action `updateEventSummary(patch, conversationId?)` en `lib/actions/event.ts`.
  `patch` acepta `{ kind, date (YYYY-MM-DD), place, place_note, time_of_day, venue, dress_code }`, todos opcionales, al menos uno, sin campos de más. Devuelve
  `{ ok: true, data: EventSummary }` (con el clima recalculado si cambió la fecha o el lugar) o `{ ok: false, error }`. Corrige el **último** resumen del hilo
  en `messages.parts`; el asesor lo ve en su siguiente turno. No manda ningún mensaje: si la persona quiere que se rehaga el look, lo pide con texto.
- Cuando `missing` no está vacío, el asesor hace **una** pregunta con `quick_replies` en el mismo turno. Tope: dos preguntas por evento (D-01); después supone en voz alta y rellena (`dress_code: "no especificado"`, `time_of_day: "day"`).
- Un evento distinto del anterior parte de cero (`new_event` en la herramienta); no hereda lugar ni código de vestir.

### 1.3 `outfit` ampliado: evidencia, refinamientos, par (C-2, C-3, D-04)

`OutfitView` gana (todo opcional):

```ts
evidence?: { kind: "palette" | "weather" | "closet" | "occasion"; label: string; swatches?: string[] /* hex, solo palette */ }[];
refinements?: { id: string; label: string; intent: ChatIntent }[];  // solo en el hilo; "Tus looks" no los trae
variant?: "seguro" | "atrevido" | null;
pair_id?: string | null;          // los dos looks de un par comparten pair_id
selected_option?: ProductOption | null;   // C-5
```

- **Evidencia** (decisión: **la guarda el servidor al proponer**, no se deriva al leer). Razón: debe decir en qué se basó *en ese momento* (la paleta o el clóset cambian después) y se produce con datos reales
  (el asesor no la escribe, BF-03). `palette` solo aparece si algún color del look coincide por nombre con la paleta activa (las muestras son esos colores); `weather` "27°" o "27° y lluvia" (≥ 40 %); `closet` "4 de tu clóset"; `occasion` la ocasión del look. Orden fijo: paleta, clima, clóset, ocasión; omite lo que no hay.
  Vive en la parte `outfit` de `messages.parts` (el hilo no necesita migración) y, si existe la migración, también en `outfits.evidence` ("Tus looks").
- **Refinamientos**: los genera el servidor desde la composición del look (no el modelo). Hasta cuatro: "Más formal", "Otro color", "Cambiar {el blazer}" (la prenda protagonista: abrigo, o arriba, o vestido), "Sin {cartera}" (un bolso o accesorio). Tocar uno = enviar su `intent` (ver §2).
- **Dos looks**: cuando el clóset da dos looks que difieren en **al menos dos prendas**, llegan **dos eventos `outfit` en el mismo turno**, `variant: "seguro"` primero y `"atrevido"` después, mismo `pair_id`. Si falta una pieza o el clóset no da dos, llega **uno** sin `variant` (D-04). El servidor valida composición de cada uno y rechaza un par que no cumple la diferencia (`checkPairVariant`).
  Guardar uno de los dos (`setOutfitStatus(id, "saved")`) es la señal de gusto; `variant` queda en la fila para medirlo (con la migración).

```json
{"type":"outfit","outfit":{"id":"570b…","title":"Blusa de seda con falda plisada","occasion":"Matrimonio de día","status":"proposed","variant":"seguro","pair_id":"75f7…",
 "evidence":[{"kind":"weather","label":"20°"},{"kind":"closet","label":"3 de tu clóset"},{"kind":"occasion","label":"Matrimonio de día"}],
 "refinements":[{"id":"r-more_formal","label":"Más formal","intent":{"kind":"refine_outfit","outfit_id":"570b…","change":"more_formal"}}, …],
 "missing_piece":null,"items":[…]}}
```

### 1.4 `search_offer` — ofrecer buscar (C-3, N9)

La persona no recibe una búsqueda que no pidió. Cuando falta una pieza y no pidió buscar, el asesor muestra primero el mejor look posible y emite:

```ts
type SearchOffer = { id: string; outfit_id: string; slot: GarmentCategory; description: string; actions: Refinement[] };
```

```json
{"type":"search_offer","id":"94b2…","outfit_id":"43d5…","slot":"shoes","description":"Sandalia o zapato de taco ancho en tonos tierra",
 "actions":[{"id":"94b2…-accept","label":"Sí, búscame opciones","intent":{"kind":"accept_search","outfit_id":"43d5…","slot":"shoes"}},
            {"id":"94b2…-decline","label":"Por ahora no","intent":{"kind":"decline_search","outfit_id":"43d5…","slot":"shoes"}}]}
```

Pinta `actions` como botones (por ejemplo como `quick_replies` en la voz de la persona). Está pendiente solo si su mensaje es el **último** del hilo (`ChatMessageView.search_offer`).

### 1.5 `shopping_options` (C-4)

```ts
type ShoppingOptionsBlock = {
  id: string;
  for_outfit_id: string | null;     // null: la persona pidió buscar y no hubo look base
  slot: GarmentCategory;            // pieza buscada (la celda "falta")
  query: string;                    // "Sandalia o zapato de taco ancho en tonos tierra"
  searched: { stores: number; results: number };   // "Busqué en 4 tiendas · 6 resultados · elegí 3"
  options: ProductOption[];         // 1 a 3, ya ordenadas
  refinements: Refinement[];        // "Más baratos", "Otro color", "Taco más bajo" (solo calzado), "No me interesan"
  trigger: "offer_accepted" | "person_request" | "refinement";
  budget_max_clp: number | null;    // el tope que se respetó
  selected_option_id: string | null;
};
type ProductOption = {
  id: string;                       // estable: "opt-" + 8 hex
  store_name: string;               // "Tienda A"
  title: string;
  price_clp: number;                // entero > 0
  seen_at: string;                  // ISO: "Visto hoy, 14 nov, 10:40 · Precio y stock pueden cambiar"
  url: string;                      // siempre https; el enlace "Ver en la tienda ↗" lo abre la persona
  image_cutout_url: string | null;  // hoy null
  image_url: string | null;         // hoy null en la búsqueda simulada: pinta el glifo de la categoría
  affiliate: boolean;               // true → insignia "Enlace con comisión" y rel="sponsored noopener"
  reason: string;
  in_stock?: boolean | null;
};
```

Reglas duras (servidor, con tests): el orden **no** usa `affiliate` (relevancia, precio, tienda: `rankCandidates`); solo `https`; precio entero positivo; `seen_at` obligatorio y no futuro;
máximo 3 opciones, sin repetidas; si la persona dio un tope (o hay presupuesto por prenda en el perfil) nada lo supera; el asesor **no puede escribir una opción**: solo existen las que devuelve `ProductSearch`.
Cuando la búsqueda no encuentra nada (o nada dentro del tope) **no se emite `shopping_options`**: solo queda el paso `Busqué en N tiendas · M resultados · ninguno sirvió` y el asesor lo dice en el texto.

**La búsqueda solo ocurre si la persona la aceptó o la pidió** (`authorizeSearch`): `accepted_offer` exige el intent `accept_search` del mismo look y pieza; `refinement` exige un `refine_search` sobre un bloque real; `person_request` exige que el asesor cite palabras de la persona que pidan buscar y que esa cita esté de verdad en sus mensajes recientes.

### 1.6 Opción elegida (C-5)

Server Action `selectShoppingOption(outfitId: string, optionId: string | null): Promise<ActionResult>` en `lib/actions/shopping.ts`. `null` quita la elección.
Solo acepta una opción que **se mostró** en la conversación de ese look (ids inventados devuelven `{ ok:false, error: "No encontramos esa opción." }`). **Elegir no compra nada**: solo marca la opción;
"Ver en la tienda" es un `<a>` a `option.url` que abre la persona. Cambiar de opción = llamar de nuevo con otro id. Solo hay una elegida por look (se quita la marca de bloques anteriores del mismo look).
Dónde se refleja: `ShoppingOptionsBlock.selected_option_id` (hilo) y `OutfitView.selected_option` (hilo y, con la migración, "Tus looks").

## 2. Intents: botones que viajan como datos (C-3)

`streamChat({ conversation_id, text, intent })` → `POST /api/chat` con `intent`. `text` es el rótulo del botón (lo que la persona ve en el hilo, requerido); `intent` es lo que entiende el asesor.
Requiere `conversation_id`. El servidor valida la forma (solo ids y enumeraciones, `strict`), verifica que **cada id sea de la persona** (y el bloque, de su conversación) y responde `400` si no. El asesor lo recibe como un bloque del sistema (`<intencion_de_la_persona>`), no como texto libre.
Pasa el `intent` **tal cual vino** en `refinements` o `actions`.

| `intent.kind` | Campos | Qué hace el asesor | Origen del botón |
|---|---|---|---|
| `refine_outfit` | `outfit_id`, `change`, `garment_id?` | Propone **un** look nuevo (sin variante, misma ocasión). `change`: `more_formal` · `less_formal` · `other_color` · `warmer` · `lighter` · `swap_garment` (+`garment_id`) · `drop_garment` (+`garment_id`) | `OutfitView.refinements` |
| `refine_search` | `block_id`, `change` | Busca de nuevo. `change`: `cheaper` · `other_color` · `other_style` · `lower_heel` · `dismiss` (no busca: pregunta qué cambiaría) | `ShoppingOptionsBlock.refinements` |
| `accept_search` | `outfit_id`, `slot` | Busca opciones para la pieza faltante | `SearchOffer.actions` |
| `decline_search` | `outfit_id`, `slot` | No busca; lo acepta en una frase | `SearchOffer.actions` |

Hoy los chips que genera el servidor usan `more_formal`, `other_color`, `swap_garment`, `drop_garment`, `cheaper`, `other_color`, `lower_heel`, `dismiss`; los demás valores existen para botones futuros.
El mensaje de la persona queda guardado con la parte `{ "type": "intent", "intent": … }`; no cambia `ChatMessageView` (sigue siendo texto).

```ts
await streamChat({ conversation_id, text: "Más formal", intent: { kind: "refine_outfit", outfit_id, change: "more_formal" } }, onEvent);
```

## 3. Cómo se reconstruye al recargar

`getLatestConversation()` (`lib/data/queries.ts`) lee `messages.parts` y arma `ChatMessageView[]` con la función pura `assembleThread` (`lib/data/thread.ts`). Lo nuevo sale de `parts`, **sin migración**:

| Parte guardada en `messages.parts` | Campo del `ChatMessageView` |
|---|---|
| `tool_step` (estado final de cada paso; uno en curso queda como `error`) | `tool_steps?: ToolStep[]` (en orden) |
| `event_summary` (el último del mensaje; `updateEventSummary` lo corrige aquí) | `event_summary?: EventSummary \| null` |
| `shopping_options` (con `selected_option_id`) | `shopping_blocks?: ShoppingOptionsBlock[]` |
| `search_offer` | `search_offer?: SearchOffer \| null` (solo si es del último mensaje) |
| `outfit` con `evidence`, `refinements`, `variant`, `pair_id` | `outfits[]` (mezcla con las columnas si existen) |
| `intent` (mensaje de la persona) | — |

`outfits[].selected_option` sale de los bloques del hilo (`selected_option_id`) y, si no, de `outfits.selected_option`. Para "Tus looks" (`listOutfits`) la variante, la evidencia y la opción elegida **solo** vienen con la migración.
Un mensaje guardado antes de esta versión no trae ninguna parte nueva: `tool_steps: []`, `shopping_blocks: []`, `event_summary: null`, `variant/pair_id/selected_option: null`, `evidence/refinements: undefined`.

## 4. Asesor simulado (`AI_MODE=mock`): qué emite en cada camino y cómo dispararlo

Es determinista y usa las **herramientas reales** (valida, persiste, emite igual que el asesor real). Necesita una cuenta con perfil completo (6 respuestas) y prendas: mándale fotos (`image_path` con la forma `{user_id}/chat/{8+ caracteres}.jpg`; en modo simulado el reconocimiento no descarga la imagen).
La búsqueda simulada (`SHOPPING_SEARCH` sin definir con `AI_MODE=mock`, o `SHOPPING_SEARCH=simulada`) usa un catálogo de ejemplo en CLP con "Tienda A…D"; solo Tienda A trae `affiliate: true`; las fotos de producto son `null`.
Con `SHOPPING_SEARCH=none` (o IA real) la búsqueda responde "no disponible" y el asesor describe la pieza.

| # | Camino | Texto de la persona (ejemplo) | Eventos, en orden |
|---|---|---|---|
| 1 | **Cuenta un evento** | `Este sábado tengo un matrimonio en Casablanca, de día, en una viña. ¿Qué me pongo? Si no tengo nada, búscame opciones.` | `text_delta` · `tool_step` (Entendí tu evento) · `event_summary` (falta `dress_code`) · `text_delta` · `quick_replies` ["Dice «formal de día»", "No dice nada", "Te mando la invitación"] · `done` |
| 1b | **Responde la pregunta** | `Dice «formal de día»` | `tool_step` evento · `event_summary` completo · `tool_step` clima (Miré el clima en Casablanca) · `tool_step` clóset · `outfit` seguro · `tool_step` clóset (`elegí N`) · `outfit` atrevido · … · `done`. Si no hay calzado adecuado (evento formal): **un** `outfit` con `missing_piece` + (si la persona ya había pedido buscar) `tool_step` búsqueda + `shopping_options`; si no, `search_offer` |
| 1c | Evento con calzado inadecuado, sin pedir buscar | `Tengo una boda de noche en Santiago el viernes, vestimenta de etiqueta. ¿Qué me pongo?` | evento → clima → clóset → un `outfit` con `missing_piece.category = "shoes"` → `search_offer` |
| 1d | Aceptar la oferta | botón `accept_search` | `tool_step` búsqueda · `shopping_options` (`trigger: "offer_accepted"`) · `done` |
| 2 | **Camino inverso** | `Quiero unos zapatos nuevos` (o `Quiero un look nuevo` → pregunta y ofrece "Quiero unos zapatos nuevos", "Quiero un blazer nuevo", "Quiero un vestido nuevo", "Quiero un bolso nuevo") | `tool_step` clóset (equivalentes) · un `outfit` con la pieza como `missing_piece` (el look no incluye esa categoría) · `tool_step` búsqueda · `shopping_options` (`trigger: "person_request"`), **sin** `search_offer` |
| 3a | Refinar el look | botón `refine_outfit` | `tool_step` clóset · `outfit` nuevo (sin variante) con la misma ocasión. Si el clóset no permite el ajuste, solo texto |
| 3b | Refinar la búsqueda | botón `refine_search` (`cheaper`: tope = precio más alto mostrado − 1) | `tool_step` búsqueda · `shopping_options` (`trigger: "refinement"`) |
| 3c | Rechazar | `decline_search`, o `refine_search` + `dismiss` | solo texto (y `quick_replies` con `dismiss`) |
| 4 | **Día normal** | `¿Qué me pongo hoy?` | `tool_step` clima · clóset · dos `outfit` (o uno) sin preguntas ni búsqueda |
| 5 | **Elegir** | (no es un turno de chat) `selectShoppingOption(outfitId, optionId)` | la opción queda marcada al recargar |

Para construir pantallas sin esperar a que la conversación llegue ahí: crea una cuenta de prueba, completa el perfil con estas 6 respuestas (`Me llamo X`, `mujer`, `casual`, `elegante`, `oficina, eventos y matrimonios`, `Nada en particular`), manda 8–10 fotos y recorre los textos de la tabla.
Los eventos se pueden ver con `curl -N` o con la utilidad `streamChat` desde el navegador.

## 5. Migración `20261114020000_compra_y_evento.sql`

Solo agrega a `outfits` (idempotente, aditiva, sin tablas nuevas, así que sin RLS ni FK compuestas nuevas: `outfits` ya tiene `outfits_own`): `variant` (`seguro`|`atrevido`), `pair_id uuid`, `evidence jsonb`, `selected_option jsonb` y un índice por par.
**La aplica Felipe antes del merge** (`DT-14`).

Sin la migración todo funciona; el código detecta "columna inexistente" (`42703`/`PGRST204`), avisa **una vez** por proceso en el log (`scope: data.outfit_extras`) y vuelve a probar cada minuto. Lo que deja de funcionar:

- "Tus looks" (`listOutfits`) no trae `variant`, `pair_id`, `evidence` ni `selected_option` (el hilo **sí**, porque vive en `messages.parts`).
- No se puede medir en la base cuál de los dos looks guarda la persona (`outfits.variant`).
- `outfits.selected_option` no se escribe (la elección sí persiste en el hilo).

Pasos de trabajo, resumen del evento, refinamientos, opciones de compra y la elección dentro del hilo **no** dependen de la migración.
